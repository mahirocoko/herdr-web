## AI diary

I began this checkpoint with an implementation that looked complete on paper,
but the session taught me to be much more literal about the evidence I accept.
The strongest moments were not the green summaries. They were the times I opened
the actual screenshots, compared them with the named state, and refused to treat
an attractive report as proof. That exposed hidden labels, the wrong mobile view,
a nonoverflowing font test, and later a keyboard menu that did not contain the
controls the user expected. I had enough context to make smaller corrections
instead of redesigning the whole product, and that preserved the existing owners.

I also felt the cost of the verification loop. A simple Stop affordance took too
many exchanges because several artifacts were invalid and a critical replacement
race had only been inspected statically. I should have required a cleaner evidence
packet earlier, including actual viewport dimensions and an explicit distinction
between executed and source-only cases. The independent replay was useful because
it found a real integration defect beyond the local component: old failures could
escape into shared App error state. Fixing only the component would have left the
user-facing problem alive. I am satisfied that the precise defect was replayed
after repair, but I must not turn that satisfaction into whole-product acceptance.
The honest stopping point is a verified implementation awaiting Mahiro's review,
with physical iOS and absent-provider live paths explicitly outside the proof.

## Honest feedback

1. Artifact quality was the biggest friction. Two confident whole-pass reports
   contained screenshots that contradicted their captions or dimensions. Checking
   the raw outputs prevented false acceptance, but repeated correction lanes made
   the process slow. State names, dimensions, visible controls and numeric geometry
   need to agree before a report can close a check. A body-overflow boolean alone
   cannot bless a control that sits outside the claimed viewport.
2. Ownership was initially wrong for More controls. Opening an existing picker was
   not enough: its empty Commands page did not provide the existing keyboard deck.
   Reusing the actual ThumbDeck inside the canonical Sheet satisfied the user job
   without inventing another key system or changing Terminal's behavior.
3. Lifecycle and integration evidence were mixed too easily. An interrupted lane
   needed receipt-bound recovery, not a success inference. A resumed process did
   not prove absence of an earlier interrupt. Component isolation did not prove
   shared App error isolation. The eventual narrow production replay resolved
   that concrete gap; another broad reviewer would not have been a better answer.

## Lessons learned

- Existing canonical guidance already requires raw-image audits, truthful proof
  layers and target-specific asynchronous ownership. This session reinforces those
  rules; it does not justify another duplicate non-canonical learning file.
- Keyboard affordance presence is not functional ownership: follow the actual
  controls to their existing producer/consumer, not the nearest convenient menu.
- Shared mutation serialization and target-specific error publication are separate
  responsibilities. Preserve busy settlement while fencing old-target feedback.
- Native status is evidence of present state, not proof of why a prior turn ended.
